# FindMyDeal reliability investigation

Investigation began 2026-11-07 at 07:04 Eastern. The observation log has a 13:16–13:58 UTC gap: the workstation journal shows suspend from 08:18 to 08:57 Eastern. Observation was extended until approximately 09:43 Eastern at the user’s request to finish. The gap cannot be reconstructed, so continuous two-hour coverage was not achieved. Evidence below distinguishes live read-only observations from tests on copied or synthetic data. The custom deployment was inspected without restarting it. Testing of alerts was excluded; AI review used controlled responses and a stubbed notification function.

## Confirmed defects and prioritized fixes

1. **P0 — Live service became unresponsive under severe resource pressure.** From approximately 14:10 UTC, repeated requests to `/api/monitor-status` timed out after eight seconds; A request for the static home page also timed out after eight seconds; ICMP ping succeeded but a new SSH connection timed out at its banner. The existing shell eventually reported load average 11.93, 145 MiB available RAM, and all 2 GiB swap used. Impact: users cannot reliably access the application while the host is stalled. The evidence does not establish whether swap pressure, process limits, browser behavior, or another cause initiated the stall. Fix plan: first capture recovery-time kernel, cgroup, Docker and application evidence; then bound concurrent browser resource use and add memory, swap, task and responsiveness telemetry and graceful degradation based on measured cause. Regression: stress the packaged deployment under constrained resources with concurrent sources and verify responsive health/status endpoints, bounded worker count and recovery without loss of saved data.

2. **P1 — Container PID 1 does not reap browser descendants.** Live container `findmydeal:reset-delay` has Node as PID 1, Docker init unset, and hundreds of Firefox-related zombies adopted by PID 1. The count rose across completed live search cycles; the recorded count had risen from 975 at 12:11 UTC to 1,096 at 14:00 UTC. The cgroup task limit is 1,882. Reproduction: run a Node PID 1 container that spawns an orphan child, wait for it to exit, and inspect `ps`; the offline control showed one zombie without init, zero with `--init`. Impact: a shrinking process/thread budget can prevent future browser or worker starts; no task-limit hit was observed in the initial samples. Fix: add and verify a proper PID 1 reaper for the container and review worker/browser termination ordering. Regression: launch and close browsers repeatedly in the built Compose image, verify orphan children are reaped, task count returns near baseline, and cancellation still works. Existing `tests/process-cleanup.test.js` accepts zombie children and does not test PID 1.

3. **P1 — Published v1.0.0 image cannot import Facebook search on Python 3.11.** Reproduction: run the server’s locally loaded `findmydeal:latest` image offline with `python3 -B -c 'import facebook_search_test'`. It exits 1 with `SyntaxError: f-string expression part cannot include a backslash` at line 176. The live custom image imports successfully, and the local working tree contains the Python-compatible change. Impact: Facebook monitoring in that published image cannot start, regardless of session validity. Fix: ship the compatible source in a new release and execute imports and marketplace module tests using the exact release image and Python version. Regression: import all marketplace modules in the built image and exercise the failing radius-error branch. The locally loaded image’s Facebook and worker files match the v1.0.0 release commit hashes; its complete image archive checksum was not independently verified. It contains Python 3.11.2, Firefox ESR 153.6.0 and geckodriver 0.36.0; the live custom image contains Python 3.11.2, Firefox 158.0.1 and geckodriver 0.36.0.

4. **P1/P2 — Page wait deadlines can be exceeded by stalled WebDriver requests.** Reproduction: point the production `WebDriver` helper at a local endpoint that holds a request open, and call `wait_for(..., timeout=30)`; the call raised `TimeoutError` after 90.0 seconds because the underlying HTTP timeout is 90 seconds. Impact: page waits can overrun their advertised deadlines, delaying recovery and occupying a source/profile; the worker has a separate ten-minute outer limit. Fix: use a single monotonic deadline and bound each transport operation by the remaining time, handling connection failures explicitly. Regression: stall individual protocol commands near the deadline and assert bounded elapsed time, meaningful error, cancellation, and cleanup.

5. **P2 — Kijiji's strict load predicate rejects usable pages.** Reproduction: serve a local redirect from a search path to a canonical path containing a valid listing, or serve a page containing a valid listing while an image request is held open. Using Firefox and the production predicate, both checks returned no result: the first had `readyState=complete` but a different path, the second had `readyState=interactive` with the listing present. Impact: search can report a load failure when the page is usable. Fix: recognize allowed canonical redirects and marketplace result/no-result/verification states rather than requiring exact original pathname and every subresource to finish. Retain bounded waits and explicit verification/block handling. Regression: real-browser fixtures for redirects, late images, empty results, verification pages, and truly stalled documents. This reproduces a weakness, not the reported live Kijiji timeout's cause.

6. **P2 — Reported `next_run` does not reflect marketplace cooldown.** At 12:11:42 UTC, live API status gave ready Facebook/Kijiji `next_run` values around 12:09, while the source schedule and 600-second delay deferred starts until approximately 12:15:35. Reproduction: let a search finish before the source cooldown expires and compare `/api/monitor-status` with `search_source_schedule`. A separate two-monitor, MariaDB-backed 403 fixture extended the source block to 60 seconds while the other monitor retained its earlier “Retrying in 10 seconds” message. Impact: users and clients can infer a run is overdue or receive a stale retry estimate even while the scheduler is correctly waiting. Fix: expose both monitor due time and effective source eligibility/block time with clear semantics. Regression: test normal cooldown, shared-source contention, blocks, and restart with database clock timestamps.

7. **P3 — Stop during the retry delay holds the profile until the delay completes.** A controlled Kijiji browser-disconnect fixture requested stop immediately after the first failed attempt. No second search ran, but the profile was still reserved 2.3 seconds later and released at 5 seconds. Fix: make the retry delay cancellable and release the profile promptly; test stop/start during retry and assert no stale run or late result.

8. **P3 — Narrow sidebar labels wrap.** At the observed approximately 427-pixel viewport, the sidebar breaks “Monitors” and “Updates” within words. Fix: give navigation enough width or use an accessible compact mobile navigation. Regression: inspect and keyboard-test narrow widths. A full-size desktop browser surface could not be opened in this session, so desktop layout coverage remains incomplete.

## Observed live service stall

At approximately 14:10 UTC the live `/api/monitor-status` endpoint failed to return bytes within eight seconds in repeated checks. ICMP ping still succeeded, while a new SSH connection timed out during banner exchange. At 14:11 UTC an existing SSH session eventually reported load average 11.93, approximately 145 MiB available RAM, and the full 2 GiB of swap in use. No live restart or configuration change was made. The simultaneous resource pressure is confirmed; whether it caused the application and SSH stall, and whether PID exhaustion was involved, remain unverified until counters or logs are available.

## External failures and hypotheses

- The live app repeatedly reported eBay 403 responses and respected its current ten-minute backoff. One run reported saving one listing before a listing-page refusal. These are application-reported statuses; no independent network trace was captured. Do not bypass the restriction. Consider a more conservative initial 403 backoff (the current coded sequence starts at 5 seconds), and use controlled 403 fixtures to test persistence and reset.
- At 12:57:26 UTC, the live app reported `Could not load Kijiji search results. Check whether Kijiji requires sign-in or verification` after starting around 12:55:40, approximately 106 seconds earlier. The reported stage was search-result recognition; no page capture or browser trace identifies the cause. The next scheduled Kijiji attempt later returned to ready by the 13:08 UTC sample. The API set the monitor due time to 13:02:26, but the source cooldown from its 12:55:40 start deferred it until approximately 13:05:40.
- A separate local-workstation Kijiji search using that workstation's profile returned `Failed to decode response from marionette` after roughly six seconds during concurrent tests. This is not proof of the live Kijiji timeout's root cause. A controlled simulated disconnect retried once after five seconds and reached ready.
- Browser version differences, resource pressure, copied-profile validity, and strict page predicates remain possible contributors to marketplace failures, but the evidence does not establish which caused the live Kijiji timeout or eBay refusal.

## Checks and boundaries

- The five marketplace/worker files compared on the live image matched the modified local checkout byte for byte. The checkout had nine pre-existing modified files; no product files were changed.
- The server's actual database was `findmydeal_migrated`; a transaction-consistent logical dump and profile copy were moved into a protected isolated workspace. The running source profiles were copied without stopping the app, so the copy is not guaranteed to be a cross-file atomic snapshot. SQLite quick checks passed for 134 copied profile databases. All copied monitors were paused, live AI credentials and alert settings were excluded.
- With server profile copies routed to a local fixture and external network blocked by profile proxy settings, source windows opened for all three marketplaces and local session detection found cookies. This does not prove remote authentication. Concurrent source opening, closing, reopening, stale-token handling, profile lock waiting, and browser-exit cleanup passed controlled checks.
- A workstation-profile eBay and Facebook search each returned a listing. The live server's blocked eBay profile was not used for extra requests, and copied server profiles were not used to generate additional marketplace traffic during the live monitors' cooldowns.
- A controlled worker cancellation terminated its process group, while a ten-minute worker limit fired at 600.008 seconds and left no matching group or monitor temporary directory. A source-window forced browser exit cleared the session and temporary display credentials.
- A real MariaDB-backed fixture started different marketplaces together, serialized same-source searches and respected a five-second start delay. A 76-second three-priority fixture gave low/normal/high 12/21/42 turns. During an interrupted five-second retry, a second search did not run but profile release was delayed.
- Monitor creation and editing, filter and item persistence after isolated restart, Items/Deals behavior with AI disabled, and keyboard selection in a custom dropdown passed sampled checks. Five controlled AI decisions produced two deals and three non-deals without a paid request or notification messages.
- Baseline and repeat automated tests passed: 29 Node tests and 27 Python tests each time. Final repeat fixtures reproduced the redirect, stalled-subresource, 403-classification, and deadline results.
